This is the installed SDK's prescribed configuration: `node_modules/@workflow/next/docs/next.mdx:84-111` explicitly requires excluding this prefix and names the detached ArrayBuffer failure caused by interception. Do not add a blanket application authentication bypass or put these requests back through session middleware to solve queue trust.

**Local queue requests are not authenticated.** In `node_modules/@workflow/world-local/dist/queue.js`:

- Lines 149-155 attach JSON content type and `x-vqs-queue-name`, `x-vqs-message-id`, `x-vqs-message-attempt` headers. No cookie, bearer token, MAC or caller signature is added by default.
- Lines 169-189 deliver POST to the generated flow/step URL using HTTP. Lines 112-113 and 156-167 also support a direct-handler shortcut, which Task 6 must not register because it would bypass the real HTTP boundary.
- Lines 262-296 validate header schemas, required body, queue prefix and JSON, then call the handler. These checks validate protocol shape, not caller identity.
- Core flow and step handlers additionally parse their payload schemas (`@workflow/core/dist/runtime.js:64-82`, `runtime/step-handler.js:19-35`). They are not HTTP authentication.
- `@workflow/core/dist/runtime/helpers.js:491-519` offers the deliberately unauthenticated `?__health` response. A 200 there proves route reachability only.

The installed Local World guide explicitly documents an in-memory queue, filesystem state, single-instance use and **no authentication**, and says it is for development (`node_modules/workflow/docs/deploying/world/local-world.mdx:80-89`). `NODE_ENV=production` for `next start` does not make Local World a production security boundary.

**Vercel's trust boundary is queue-only platform routing, not a signature in this application's route.** `@workflow/world-vercel/dist/queue.js:251-295` delegates to `QueueClient.handleCallback()`. In installed `@vercel/queue/dist/index.js:2228-2260`, that callback parses the request and processes the queue message; it does not verify a caller HMAC. The Vercel World guide documents that generated `experimentalTriggers` restrict handler access to Vercel Queue (`workflow/docs/deploying/world/vercel-world.mdx:175-201`). The Next builder emits those triggers (`@workflow/next/dist/builder-eager.js:332-350`; `@workflow/builders/dist/constants.js:30-38,60-68`). `CANDIDATE/app/.well-known/workflow/v1/config.json` has both `queue/v2beta` triggers, topics `__wkf_step_*` and `__wkf_workflow_*`, consumer `default`.

Do not claim the installed callback always fetches a payload using only a message ID: the guide's line 198 is incomplete for this version. `@vercel/queue/dist/index.js:706-763,797-839` also accepts a binary CloudEvent carrying a receipt handle and body, then calls `consumeMessage`. Correct platform routing is therefore essential; copied Vercel headers are not an authentication scheme for a public self-hosted endpoint. OIDC authenticates backend operations; it does not supply application-cookie authentication to local queue delivery.

**Security constraints / external release gate:** Task 6 must bind the entire local app to `127.0.0.1`, use an explicit matching `WORKFLOW_LOCAL_BASE_URL`, a private isolated data directory and synthetic local Supabase records only. No tunnels, LAN binding, public ingress or remote provider credentials. Do not release that topology publicly. A Vercel release needs evidence that the final deployed handlers have platform queue-only protection; a self-hosted production choice needs a production-capable World and ingress/worker trust design. The installed self-hosted guidance recommends network-edge restriction, avoiding framework middleware body handling (`workflow/docs/deploying/world/postgres-world.mdx:245-265`); its exact routes/topology must be adapted, not assumed identical to Local World. No such production changes or remote verification are authorized/performed in this preparation.

## 2. Queue startup, persisted identity and restart

**Recovery exists, but its automatic activation by this app is not established.**

- `@workflow/world-local/dist/index.js:65-106` constructs queue/storage and exposes `start()`. That method initializes the data directory and calls `reenqueueActiveRuns`; merely constructing the World does not call it.
- Recovery defaults on, subject to `WORKFLOW_LOCAL_RECOVER_ACTIVE_RUNS` or factory configuration (`world-local/dist/config.js:16-36`). This controls what `start()` does, not whether startup happens.
- `@workflow/world/dist/recovery.js:12-39` lists persisted pending/running runs and queues `{ runId: run.runId }` under each stored workflow name. It preserves the run ID; it does not create a replacement run.
- `@workflow/core/dist/runtime/world.js:69-94` caches Worlds globally. `getWorld()` returns a synchronous World in 4.x and neither it nor `getWorldHandlers()` calls `start()`. Version-specific docs confirm the synchronous contract (`workflow/docs/v4/api-reference/workflow-runtime/get-world.mdx:20-22`); `await getWorld()` remains compatible.
- `@workflow/core/dist/runtime/start.js:42-75` gets the World to launch a **new** run, without invoking the World lifecycle method. The names `start(workflow, args)` and `world.start()` must not be conflated.
- Targeted searches of installed core, Next adapter and builder runtime sources found no caller of `world.start()` / optional equivalent. The candidate root, `src` and `.next/server` have no instrumentation entry. This is strong source evidence for a missing app startup hook, not an executed restart failure.
- The local queue holds in-flight work/idempotency state in memory (`world-local/dist/queue.js:107-135`). Filesystem runs/events/steps survive only if the same absolute `WORKFLOW_LOCAL_DATA_DIR` is preserved. Its default is relative `.workflow-data` (`config.js:4-5`). Use the same candidate, data directory and namespace after restart; do not rebuild or clear state mid-proof.
- Recovery can redeliver a run while completed-step outputs remain in its event history. Retry records are persisted as `step_retrying`, and the step is set pending (`core/dist/runtime/step-handler.js:595-639`). App `dispatchAssessmentJob` stores the original Workflow run ID (`lib/server/workflows/index.ts:10-25`). App-level redispatch or `recreateRunFromExisting` creates a new run and cannot prove same-run recovery (`core/dist/runtime/runs.js:10-26`).

**Supported proposal if Task 6 reproduces missing recovery:** add an actual application startup integration under the implementation owner's control. `world.start?()` is an official lifecycle method (`workflow/docs/deploying/building-a-world.mdx:33-43`). Workflow's Next/Postgres example uses `instrumentation.ts` → `register()` → `getWorld().start?.()` (`workflow/docs/deploying/world/postgres-world.mdx:84-100`). Applying that lifecycle pattern to Local World is a proposal based on its actual `start()` implementation, not a claim that the example already proves Local World acceptance.

Read the installed Next guide before implementing: `node_modules/next/dist/docs/01-app/02-guides/instrumentation.md:17-19,70-82` specifies once per server instance, completion before readiness, and runtime-specific imports. Explicitly check startup readiness: recovery begins asynchronous self-HTTP deliveries, and the local queue's transport-exception catch only logs (`queue.js:233-253`), so a premature connection failure could strand work. The final artifact must contain the integration, pass the applicable checks and restart unaided. A test preload calling `world.start()`, injecting `setWorld`, registering direct handlers, or manually re-enqueueing cannot establish automatic application recovery.

## 3. Generated step execution and synthetic provider

**The generated model call executes in the host Node context.** The generated `CANDIDATE/app/.well-known/workflow/v1/step/route.js:25-32,291-304` imports AI SDK and app dependencies and registers the real assessment step. `@workflow/core/dist/runtime/step-handler.js:137,417-439` resolves that function and calls `stepFn.apply(...)` inside AsyncLocalStorage. It does not execute that step in the Workflow VM. Workflow orchestration itself does use a fresh VM (`@workflow/core/dist/workflow.js:69-86`), so a host global must not be assumed visible inside workflow-body code.

The app passes a model string via `llm.structured()` (`lib/shared/llm/models.ts:3-14`; `generateAssessmentStep` in `lib/server/workflows/generate-assessment.ts`). Installed AI SDK resolves string models through `globalThis.AI_SDK_DEFAULT_PROVIDER ?? gateway` (`node_modules/ai/src/model/resolve-model.ts:26-43,186-188`). The global override is documented in `node_modules/ai/docs/03-ai-sdk-core/45-provider-management.mdx:327-337`.

This hook survived the candidate's compilation: `CANDIDATE/.next/server/chunks/_18mx71lcw_69p._.js` contains the `globalThis.AI_SDK_DEFAULT_PROVIDER` lookup and is directly required by the compiled step route. `CANDIDATE/.next/server/chunks/_0dzfz1cxpqk-4._.js` contains `generateAssessmentStep` and its `maxRetries=3`. The compiled flow asset `_1v9v53ue771yi._.js` carries the separate workflow program string.

An external Node preload that sets only this documented provider hook is a viable Task 6 approach. Start the actual Next CLI process with the preload, not just an unrelated launcher process. Installed `next/dist/cli/next-start.js:104-110` calls `startServer({ isDev: false, ... })` directly. The inspected Workflow step path has no process/VM boundary of its own. If a launcher forks or spawns a fresh Node process, an in-memory global in its parent does not transfer: pass the preload to that exact child (and every restart), and verify its PID/ledger from real step execution. These source facts support the approach; they do not prove the final launched route sees the hook.

The synthetic provider must implement the installed AI SDK language-model contract, support only expected model IDs, produce schema-valid synthetic results and fail closed for unexpected calls. No fallback provider. A missing global falls back to Gateway, so credential omission alone is insufficient proof: launch with a minimal sanitized environment and an outbound-network boundary allowing only the explicitly selected local app/Supabase addresses; record denied attempts. A provider invocation ledger should contain only synthetic identifiers/attempt counters/PID and result markers, never credentials or real transcript data. Do not modify generated bundles, replace app modules, monkeypatch Workflow lifecycle, or claim an isolated Node smoke result proves the compiled HTTP route.
