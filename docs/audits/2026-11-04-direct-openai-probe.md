# Preview OpenAI direct smoke: isolated prototype, DO NOT DEPLOY

This is a review artifact on the isolated probe branch, not a completed feature, a deployment, a Supabase migration, or permission to call OpenAI. It has made no provider calls and touches no hosted data. The prior USD 5 authorization was for existing AI Gateway credits, not direct OpenAI billing.

**HOLD — NO HOSTED WRITE.** The profile preflight/44-row readback and the proposed chronology 45-row readback require `audit_log=0`. This prototype's marker would make those exact checks fail, including after the chronology readback. Within the handler, `verifiedHostedReadback()` runs before the handler's authentication, reservation or generation; it **always returns false and cannot be enabled by environment configuration**. Invoked directly with all other flags on, the handler returns 404 before those operations. The full deployed request can first pass through `proxy.ts`, which calls Supabase Auth `getUser` and can redirect to login before the handler is reached. Vercel protection may also intercept it. Neither the deployed proxy-to-handler flow nor its response has been tested end to end. The tests that exercise later steps explicitly substitute a fictitious receipt gate; they are not proof of an actual receipt. Do not replace this hold with a feature flag or a claimed receipt.

## Intended behavior and boundaries

If the HOLD is later replaced by a reviewed mechanism, the endpoint `POST /api/internal/openai-probe` would additionally require Vercel runtime, production NODE_ENV, Preview environment, the disposable `codex/serenia-openai-direct-probe` branch, `OPENAI_PROBE_ENABLED=on`, direct OpenAI transport, the exact reviewed Supabase project URL, and exact HTTPS Origin from the platform's `VERCEL_URL` deployment domain. It does not trust Host/forwarded headers or accept prompt/model/schema input. Authentication is `getUser` and the existing explicit pilot allowlist, which remains unverified in Preview. This prototype is not suitable for production. Normal Vercel deployment authentication must remain enabled; do not use `vercel curl` or create a bypass token.

Both task policies must resolve to `openai/gpt-6-luna` and `openai/gpt-6.1-sol`, respectively, and use the existing direct resolver. A single permanent UUID row in `audit_log` is inserted by service role before provider execution; no conflicting row can win. Insert retries are disabled and an ambiguous response stops the request. If the insert commits but its response is lost, the single opportunity is consumed. Do not delete or reset the marker to re-run. The one-shot guarantee is conditional on the exact database, normal PostgreSQL uniqueness, no administrative deletion/restore or unauthorized writes, and the runtime adapter behaving as reviewed. It is not a provider-enforced spending limit or a guarantee against every intermediary replay; an account-level budget would be stronger.

The two generations are sequential with fixed fictional prompts, no tools, one step, `maxRetries=0`, 1,000 output tokens each, and 45-second timeout. First failure, missing/invalid usage, incomplete text, or out-of-range usage stops the second call. The installed AI SDK forwards the timeout abort signal to its fetch; an upstream provider can still process or bill a request after the local client aborts. The report uses a tiny Zod schema; no clinical user data is sent. Only status and usage counts are returned. The resolver adds `store: false` but this alone does not establish all provider retention or clinical privacy obligations. Input requests are fixed and the synthetic captured bodies are less than 8,000 bytes each; the 8,000-token check is post-response and **is not a provider-enforced input-token cap**. Reasoning tokens can exhaust the output allowance and make a response incomplete without proving lack of model access.

As an estimate only, applying 2.5x cache-write input pricing and 10% regional premium to hypothetical 8,000 input and 1,000 output tokens for each call gives $0.05775 before tax; pricing and account eligibility must be rechecked before seeking direct OpenAI spend approval. The design does not enforce this amount at the provider. It would establish simple text/structured direct transport only, not chat streaming, tool execution, durable workflows, extraction quality, reports, availability of accounts, clinical accuracy, or legal acceptability.

## Local evidence

Run `rtk npm run openai:probe:test` from the repository root. This explicit gate runs the synthetic tests, Next handler tests and a disposable local PostgreSQL rehearsal; Docker access may require local sandbox permission. Logs from `npm run verify` remain in its private evidence directory.

Tests use `MockLanguageModelV3`, `globalThis.fetch` replaced with an in-memory fake for direct transport, and a Supabase client with an injected fake fetch. They check the exact two fixed model bodies, `store: false`, maximum output, no tools, SDK abort propagation and no retry on synthetic failure, concurrency and lost-response behavior at the fake data boundary, and no provider call when guards fail. The Next `POST` handler is called with synthetic requests, fake Supabase client and fake generation; tests cover flag-off, the real allowlist function, reservation and two model calls in order. They do not verify a real authenticated session or deployed Next runtime. An additional test uses 12 separate concurrent PostgreSQL 17.6 transactions inside an ephemeral, network-disabled container. The runner creates a nonce-named schema with two separate synthetic tables; the tests use only INSERT and SELECT there, without TRUNCATE or writes to `public`. The test verifies the Unix socket when constructing the target; before each SQL command it checks the full container ID, name, random label, exact image reference and `network=none`. Direct invocation with forged environment is tested against a fake Docker executable: invalid variables cause no Docker invocation and a mismatched identity never reaches `docker exec`. The latter test skips when no local Unix socket exists. The PostgREST transport and table/roles are synthetic. The Docker test runs with RTK when installed and Docker directly otherwise; a PATH omitting RTK simulates this locally, not on an actual Linux runner. These checks prevent accidental targeting, but a hostile Docker administrator can spoof labels or change state between inspection and execution. A local Unix socket can itself be a proxy; SIGKILL or late daemon creation can prevent automatic cleanup. No test exercises real Supabase Data API, actual authentication, deployed Next behavior, preview deployment protection, or real OpenAI. The probe is isolated on its dedicated branch and is not intended to enter the pilot branch or main.
